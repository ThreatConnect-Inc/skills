# Write-path API notes (confirmed against instance A, Oct 2026)

- Auth: `Authorization: TC <TC_KEY>`; credential lives in a per-instance env file (`.env_instanceA`, `.env_instanceB`, ...). The env file holds only `TC_KEY`, NOT the base URL — ask the user for it.
- Read full definition: `GET /api/v2/playbooks/{id}`. Resolve ids via v3: `GET /api/v3/playbooks?tql=groupXid EQ "..."` or `name EQ "..."`.
- **Update in place:** `POST /api/v2/playbooks/{id}` with the full definition JSON as the body. `PUT` on v2 returns 405. (`OPTIONS` shows v2 id allows HEAD/DELETE/POST/GET; v3 id lists PUT but is untested.)
- **Versioning (confirmed):** every POST creates a NEW version (1.0 -> 2.0 -> 3.0) with a NEW numeric id that is not predictable (e.g. ...532 -> ...533 -> ...534). New versions are Draft/inactive. The original published version keeps its id and content, and it is the only one that v3 TQL lookups, the v2 list, and `GET /api/v2/playbooks/<groupXid>` return. The new draft id is only in the POST response, so **record it** (push_playbook.sh logs it in CHANGELOG.md and saves `_after.json`). Drafts can be fetched with `GET /api/v2/playbooks/<draftId>`.
- Consequence: `before` backups taken via groupXid lookup are the published version, not necessarily the latest draft. To iterate on a draft, fetch it by its draft id from CHANGELOG.md.
- **POSTing to a draft id does not overwrite it** — it creates yet another version (confirmed on instance D: 1.0 -> 2.0 -> 3.0, each with a new id, earlier ones unchanged). So versions accumulate; each push is non-destructive, and `_before`/`_after` files plus CHANGELOG ids are the map.
- **Create from scratch (confirmed on instance D):** `POST /api/v2/playbooks` with a full definition JSON (e.g. a downloaded export) creates a new playbook at version 1.0, Inactive. Change `name` and `groupXid` first so it doesn't collide with the source (a fresh 9-char xid like `ZZclaude1` was accepted). Instance-specific ids embedded in the export (appCatalogItem ids, languageModelConfiguration id) were accepted across instances (instance A export -> instance D), with jobs/trigger/connection/model slug intact.
- The credential for a shared UAT instance is for that instance only; it is shared with other people's playbooks (527 at last count) — only touch playbooks you created, and name test ones clearly (e.g. "ZZ ... - delete me").
- **MCP (`mcp__threatconnect__*` or `mcp__plugin_cti_dataminr-atip__*`) is read-only for playbooks:** `tc_resources` lists `playbooks` as `writable: false`; `tc_list` returns metadata only (the `query` arg I tried didn't filter), `tc_get` on a playbook returns 405 (same v3 limit). Use MCP only for discovery; all full-definition reads and all writes go through direct v2 API.
- **Activate / deactivate (confirmed on instance D):** `POST /api/v2/playbooks/{id or groupXid}/activate` and `.../deactivate`. Activating a **draft id** promotes it: the version gets a minor bump (3.0 -> 3.1), status becomes Active, and from then on v3 TQL and `GET /api/v2/playbooks/<groupXid>` return that version. Deactivating by groupXid returns Inactive but the promoted version stays the published one (it does not revert to 1.0). So "publish" = activate the draft id, then deactivate if it shouldn't stay running. Only activate when the user asks — an active playbook with an HttpLink/Timer/Mailbox trigger can start doing real work.
- **Delete:** `DELETE /api/v2/playbooks/{id or groupXid}` (per docs; not exercised by Claude — deleting is a user action, hand them the command or the Designer link).
- Open question (untested): whether old draft versions can be deleted individually.
- Updated playbooks come back `status: Draft`, `active: false`.
- Body is the same shape the GET returns: edit `jobList[].jobParameterList[]` (match on `appCatalogItemParameter.paramName`, e.g. `systemPrompt`, `userPrompt`), `languageModelConfiguration`, etc. Keep everything else untouched.
- `POST /api/v2/playbooks/import` also exists (untested; likely creates a new playbook).
- MCP: the `mcp__threatconnect__*` or `mcp__plugin_cti_dataminr-atip__*` tools are bound to ONE instance (previously instance D) and cannot target another per call. Use direct API for any other instance. Check which instance the MCP points at before trusting it.
- **Webhook endpoints (confirmed on instance A):** the trigger `endpoint` (`<base>/api/playbook/<uuid>`) differs between versions (the v2 POST response, the v3 listing and later activated versions showed different UUIDs). A call to a stale/inactive endpoint returns `404` with an empty body. Always resolve the current endpoint right before calling (`playbook_ctl.sh status` / `test_webhook.sh` do this). GET and POST both work on the example webhook with no auth header.
- **Version numbers:** push = new major (4.2 -> 5.0); activate = minor bump on the activated version (5.0 -> 5.1; activating again -> 5.2/5.3).
- **Worked test (instance A `<id-A>`, 2026-10-13):** Set Variable `user.request` = "...past week" -> webhook returned `2026-10-06`; edited to "...past 30 days" via push_playbook.sh, activated draft, webhook returned `2026-09-13` (expected, today 2026-10-13). Outputs saved under `playbook-testing/playbook-backups/<id-A>/`.
- **v2 Group/Owner endpoints can 400 even with correct auth, on an instance where v2 Playbooks works fine (confirmed on instance C, 2026-10-20).** `GET /api/v2/groups/reports/{id}`, `/api/v2/groups/{id}`, and `/api/v2/owners` all returned `{"status":"Failure","message":"The request was not properly formed"}` / HTTP 400 — not an auth problem (the identical `Authorization: TC <TC_KEY>` header works fine against `/api/v2/playbooks/{id}` on the same instance). Don't assume "v2 works here" generalizes across resource types on a given instance; the v3 equivalents (`GET /api/v3/groups/{id}`, `/api/v3/owners`, etc.) worked immediately. Test the specific v2 endpoint you need before building a script around it, rather than assuming parity with v2 Playbooks.
- **Downloading a Report/Document group's actual attached file (confirmed on instance C):** `GET /api/v3/groups/{id}/download` returns the raw file bytes directly (no JSON wrapper, no auth beyond the usual header). The old v2 `reportFileData` endpoint 400'd (see above), and there is no `fields=` option on the v3 group GET for this (`fields=fileData` is rejected with `Unrecognized fields parameter`). Useful for pulling a real HTML report body to test an HTML-parsing/conversion job's input against actual data before building the job, not just trusting the playbook's own regex/JMESPath to behave as expected on unseen input shapes.
- **Attribute type limits and Markdown support are queryable (confirmed on instance C):** `GET /api/v3/attributeTypes` (paginated, `resultLimit` works) returns every attribute type with `maxSize` (character limit) and `allowMarkdown` (boolean) per type, e.g. `Description` had `maxSize: 102400, allowMarkdown: true`. Check this BEFORE wiring a Base Agent / long-generated-text job's output into an Attributes app's `attribute_values` — a generated summary, Markdown conversion, or anything that can scale with input size (especially if it might carry embedded binary like base64 images) can silently exceed `maxSize`; there's no guard against this in the Attributes app params themselves; see `playbook-explorer/references/best_practices.md`'s new ATTR-1 item.
- **`GET /api/v3/owners` is NOT a real endpoint on at least one instance (confirmed on instance C, 2026-10-22: HTTP 404), contradicting an earlier note in this file that it "worked immediately."** Don't assume a v3 endpoint exists on a given instance just because the equivalent v2 endpoint 400'd or because a similarly-named one worked elsewhere — verify each specific endpoint directly. (Owner lookups that DO work: TQL `ownerName` filters on `/v3/groups`, `/v3/indicators`, etc.)
- **Setting an attribute via v3 has no dedicated sub-resource endpoint — use the same PUT-with-mode pattern as tags (confirmed on instance C, 2026-10-22).** `POST /v3/groups/{id}/attributes` is not a real route (404 "Resource not found"). The actual mechanism: `PUT /v3/groups/{id}` with body `{"attributes": {"data": [{"type": "Description", "value": "...", "source": "..."}], "mode": "append"}}` — the same `{data, mode: "append"|"delete"}` shape v3 uses for tags (`{"tags": {"data": [{"name": "X"}], "mode": "append"}}`, confirmed both add and remove). Try this shape first for any v3 nested-collection field (attributes, tags, associations) before assuming a separate sub-resource endpoint exists.
- **Uploading a Report/Document group's file content requires `Content-Type: application/octet-stream`, never the file's real mime type (confirmed on instance C, 2026-10-22).** `POST /v3/groups/{id}/upload` with `Content-Type: text/html` (or presumably any specific media type) returns a generic, non-diagnostic `HTTP 500 "An unknown error has occurred"` with no indication of what's wrong. The fix was found by trying a couple of `Content-Type` values on a disposable probe group, not from any error message. Also: the group needs `fileName` set (either in the initial `POST /v3/groups` create body, or via a prior `PUT /v3/groups/{id}` with `{"fileName": "..."}`) before upload succeeds. Order: create with `fileName` set -> `POST .../upload` with an `application/octet-stream` body.
- **An unscoped TQL query across common types can return org/global reference data, not just your own playbook's output — always scope by `ownerName` when sanity-checking what a playbook created.** Confirmed: `typeName in ("Intrusion Set", "Malware")` with no owner filter returned 200+ results instance-wide (a shared CAL Automated Threat Library's own MITRE-derived catalog — `EMBARGO`, `APT28`, `WIZARD SPIDER`, etc.), which looks identical to "the cleanup/reset didn't work" if you're expecting an empty result. Add `and ownerName in ("<your owner>", ...)` before trusting a count as confirmation of a clean slate or of what a specific run created.
- **A probe-and-delete pattern is the fast way to nail down an uncertain v3 write shape.** For both findings above, the fastest path was: `POST /v3/groups` a throwaway group (clearly named, e.g. "ZZ <what you're testing> - delete me"), try the write against it, inspect the result, iterate, then `DELETE` it when done — confirming a write mechanism this way before touching real data avoided guessing blind against a playbook's actual output.
- **`cut -d= -f2` silently truncates a `KEY=value` line's value if the value itself contains an `=` character — which API tokens commonly do (base64-style padding).** Confirmed: a working, valid, 180-day token stored in an env file as `TC_KEY=APIV2:....=` was being extracted with `grep '^TC_KEY=' .env_file | cut -d= -f2`, which returns only the text between the *first* and *second* `=` — silently dropping the trailing `=`, and every API call then failed with a clean 401, which looked exactly like an expired/invalid/wrong token (and was initially misdiagnosed as such, including asking the user to regenerate a token that was never the problem). Use `cut -d= -f2-` (the trailing `-` means "field 2 through the end") or a proper parser (`python3 -c "import os,sys; ..."`, `source`-ing the file, etc.) whenever extracting a credential or token value this way, never a plain `-f2` or similar fixed-field split. If an auth failure appears right after a credential was "just updated" and looks inexplicable, check your own extraction command before concluding the credential itself is bad.
- **Pushing a playbook can reassign job ids on every single push for some edits, not just "when adding new jobs" as a plain reading of the normal push/rewrite behavior suggests.** Confirmed: a sandbox job's numeric id changed on every consecutive push while iterating on it, most reliably triggered by swapping a job's `appCatalogItem` (e.g. a Base Agent replaced in-place by a JMESPath job under the same slot in the edit) — after which even subsequent, content-only pushes to that job kept reassigning its id on every following push too. In the same cases, the server DID correctly auto-rewrite internal `#App:` cross-references to match the newly assigned id on each push (including the trigger's own `httpResponseBody` field) — so the fix is not to fight the renumbering, it's to never hardcode a job id you read before a push into anything you still need to be correct after that push: always re-fetch the live/draft definition after pushing and read the real id back out before using it (e.g. in a follow-up push, or when calling the webhook) rather than trusting the id from your own edit file.

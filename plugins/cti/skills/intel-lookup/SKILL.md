# TIP Intel Lookup

Retrieves and synthesizes threat intelligence from a ThreatConnect/Agentic TIP instance, via either the TIP MCP server (preferred) or direct v3 REST API calls (fallback). Handles entity lookups, daily triage, industry/country scans, and report generation. (PIR/intel-requirement briefings are currently paused — see below.)

## Before anything else: which access path is available?

Check the current tool list for `tc_resources` / `tc_list` / `tc_describe` / `tc_get` / `tc_create` / `tc_update` / `tc_delete` (named `mcp__threatconnect__*` when added by hand, or `mcp__plugin_cti_threatconnect__*` when it comes from the `cti` plugin; load via tool_search if deferred).

**This skill currently operates MCP-only.** Direct API access (`reference/direct_api_fallback.md`) is documented for a future release but not currently wired into any workflow below — the security tradeoff of passing a raw API token through chat wasn't one the customer wanted to accept yet, and there's no secure channel in this environment to supply it otherwise (unlike MCP, where the token exchange happens outside the model's context entirely).

- **MCP tools available** → use them. This covers the great majority of what this skill needs — see the confirmed resource-type list in `reference/direct_api_fallback.md` if curious what's in scope.
- **MCP tools not available** → tell the user the TIP MCP connector needs to be enabled before you can pull live data. Don't guess at intel from memory, and don't offer direct API as a fallback in the meantime — it's not currently supported in this skill.

Everything below is written in terms of MCP tool calls.

## Customer context (read/build this first)

Check for a `customer_context.md` already created for this engagement (in the project or conversation working notes). If it doesn't exist yet, use `reference/customer_context_template.md` as the shape to build one — per customer, on first use, not bundled as static data.

It should capture, once, and reuse afterward:
- **Industry** and **country/region** (needed for "impacting my industry/country" queries)
- **Watchlist** — named actors, malware, CVEs, or tags they care about
- **Priority signals** — how *this* customer wants "what should I prioritize" ranked. Ask explicitly: some combination of recency, severity/confidence attributes, specific tags (PIR matches is currently excluded — see the paused PIR section below). Don't assume a default weighting — different SOCs prioritize differently.
- **Owner/source scoping** — which TIP `owner` (org/community/source) to query by default, since large instances mix raw wire feed (e.g. Dataminr Pulse events) with curated intel (CAL Automated Threat Library, internal analyst-authored reports).

Ask for a given field **only when a query actually needs it** — don't front-load a big intake questionnaire. If missing when needed, ask once, confirm, then save it for the rest of the engagement — don't re-ask every turn.

## Core retrieval pattern (use for almost every query)

Most useful answers require **more than one lookup** because intel in a TIP is a graph, not a flat table: a Report about a CVE may link to a Vulnerability group, an Intrusion Set, and a pile of IOCs. Follow this pattern:

1. **Classify the query** into one of the workflows below.
2. **Anchor search — prefer unified-object queries first.** For CVEs and threat actors specifically, the platform auto-consolidates multiple feeds' records into a single normalized object. Use `hasCommonVulnerability(summary = "<CVE-ID>")` / `hasThreatActorProfile(summary = "<MITRE primary name>")` (wrapped in `hasGroup(...)` when searching `Report`/`Event`, used directly when searching `Vulnerability`/`Adversary`/`Intrusion Set`) rather than reconciling per-owner records yourself. **Always add `fields=common`** on these queries to get the platform's own normalized CVSS/KEV/profile data. Read `reference/unified_object_queries.md` before writing these — it documents confirmed syntax, the alias-resolution limitation (MITRE primary name only), the non-MITRE-actor gap (no profile exists for many ransomware groups), and the fallback plain-group query to use when a unified object doesn't exist yet (very fresh CVEs) or can't be resolved (aliases, non-MITRE actors). For everything else, search `groups` scoped by `typeName` and/or `indicators` using TQL — **read `reference/tql_reference.md` before writing any TQL**, the query keyword for text search (`summary`) is NOT the same as the display field (`name`), and other resource types have their own gotchas (including an important exact-match vs. contains distinction for Vulnerability groups).
3. **Topic/keyword searches (not just named entities) should also check tags, not only `summary CONTAINS`.** A topic like "supply chain attacks" or a country/region name may be captured as a dedicated tag on a report without appearing in that report's own title. Combine `summary CONTAINS "<topic>"` with `hasTag(name CONTAINS "<topic>")` for broader, more reliable recall — don't rely on title-text matching alone for open-ended topic asks.
4. **Apply a default recency bound on "what's happening/latest" framed topic searches when the user gives no timeframe — don't return the full unbounded history.** 30 days is a reasonable default. This applies to activity-framed asks ("what's happening with X," "latest on X") — it does **not** apply to a pure background/descriptive ask ("tell me about X," where full historical context may be exactly what's wanted); use judgment on which framing the user's question actually has.
5. **Triage before expanding** — a broad search can return hundreds of hits (e.g. "APT28" alone returned 128 reports in testing). Use `summary: true` list mode first to see volume and skim titles/dates, then pick the most relevant/recent handful before doing expensive full expansion. **For hits found via `hasGroup(hasThreatActorProfile(...))`/`hasGroup(hasCommonVulnerability(...))`, treat them as candidates, not confirmed relevance** — bulk automated enrichment can attach broad, boilerplate actor/TTP associations to generic articles with no real substantive connection (confirmed live — see `reference/unified_object_queries.md`). Skim the actual title/summary before including a hit.
6. **Expand associations** on the selected anchors — pull `associatedGroups`, `associatedIndicators`, `associatedVictimAssets`, `tags`, `attributes` via the `fields` parameter. See `reference/association_traversal.md` for how to do this without blowing context (caps, pagination, when to stop expanding), **and for the "association by proxy" pattern** — IOCs and victims are very often linked to the *Report/Event about* an actor or CVE rather than to the actor/CVE object directly, and both need surfacing to give a complete picture.
7. **Surface victims explicitly when present.** Who was targeted/affected (org, sector, region) is high-value to users and easy to miss since it isn't in the free-text summary — check for `associatedVictimAssets`/`victims` on anchors and their linked Reports/Events, not just IOCs.
8. **Assemble + dedupe across sources.** TIP feeds often carry the same story from multiple owners/sources (e.g. CAL, VulnCheck, Dataminr Pulse all publishing on the same CVE). Consolidate into one narrative by default — don't repeat the same fact three times — but explicitly call out anything one source adds that the others don't (e.g. only VulnCheck carries exploitation/KEV metadata; only CAL carries the ATT&CK-tagged narrative). Only skip consolidation if the user asks to see sources separately.
9. **For CVEs/vulnerabilities specifically, always surface:** CVSS score/vector, affected products/CPEs, and exploitation status (KEV listing, weaponization, public/commercial exploit availability) if present in the data — these are the fields users need to gauge urgency and are easy to bury in a narrative summary.
10. **Always include the "what to do about it" alongside "what it is."** Vendor remediation guidance, patch versions, workarounds/mitigations, and course-of-action recommendations from the source reporting are as important as the technical description — don't stop at describing the threat.
11. **Synthesize in plain language.** Lead with what matters (is this relevant to the customer, how severe, how confident, what to do), not a raw data dump. Cite counts/dates/sources naturally.
12. **Cite and link, selectively.** Every object carries a `webLink` back to the platform. Link the 1–3 items an answer's key claims actually rest on, and the unified object (see below) once as a "start here" — not every hit in a large result set. Read `reference/citations_and_links.md` before doing this; it also covers when (and only when) to offer the user a copy-pasteable TQL query for browsing a large result set themselves, which should be an offer, never an automatic addition.
13. **Offer — don't auto-generate — a report.** See Report Generation below.

## Workflows

### Entity lookup — "tell me about CVE-X" / "latest on [actor]" / "intel on [malware/campaign]"
- **CVE or actor entities:** try the unified-object query first (`hasCommonVulnerability(summary = "<CVE-ID>")` or `hasThreatActorProfile(summary = "<MITRE primary name>")`, with `fields=common`) — see `reference/unified_object_queries.md` for confirmed syntax and fallback logic when the unified object doesn't exist (very fresh CVE) or can't be resolved (alias instead of primary name, or a non-MITRE actor like most ransomware crews). Fall back to a plain `typeName`-scoped group search (`summary EQ` for Vulnerability, `summary CONTAINS` for everything else) when it does.
- **Resolving the entity is only step one — always chain a second query for recent associated intel, don't stop at the entity object itself.** Run `typeName IN ("Report","Event") AND hasGroup(hasCommonVulnerability(...))` / `hasGroup(hasThreatActorProfile(...))` scoped to a recency window (7 days is a reasonable default) to see what's actually happening with this entity, not just that it exists. If that comes back empty, extend the lookback (e.g. 30 days) before concluding there's nothing new. For a MITRE-tracked actor, **run this association query together with the literal-alias-mention query** (`summary CONTAINS` across known aliases) — not one instead of the other — since they catch different things (see `reference/unified_object_queries.md`'s "two genuinely different questions" section); treat the association hit as the stronger signal when both surface the same item, and present literal-only mentions as a secondary, clearly-labeled list. For a non-MITRE actor (no profile to query), skip the profile half but still chain the recent-activity query using the literal name/alias — don't stop at just returning the raw actor-object records across owners.
- **Malware/campaign entities** (no unified-object equivalent): anchor search across `groups` (`typeName` in Report, Incident, Malware, Campaign, Event as relevant) with `summary CONTAINS "<entity>"`, then chain the same "find recent associated intel" step as above.
- If the entity is a CVE ID, also check `indicators` — CVEs sometimes exist as their own indicator/attribute rather than only inside report text.
- Expand top hits' associations to build full context (linked actor ↔ malware ↔ vulnerability ↔ IOCs ↔ victims). Remember IOCs and victims are frequently linked to the *Report/Event about* the entity rather than to the entity object itself — see the "association by proxy" pattern in `reference/association_traversal.md`.
- **IOCs are a secondary, complementary addition here — not the default lead.** After presenting the group/topic-based intel, it's worth also surfacing any new high-severity IOCs tied to the entity (via the same association-by-proxy or topic-tag pattern, combined with the score filter from `reference/ioc_scoring_and_topic_queries.md`) as an actionable add-on the user can act on immediately. Don't lead with IOCs, and don't run the IOC-scoring pattern unless the user actually asked about IOCs specifically or it adds clear value alongside the main answer — a short "Associated high-severity IOCs" note is a value-add, not a replacement for the group-based answer.
- For CVE/vulnerability entities: lead with CVSS score/severity, affected products/CPEs, exploitation status, and the vendor's actual remediation guidance (patched versions, workarounds) — not just a narrative description. Prefer the normalized `commonGroup` CVSS/KEV data over any single feed's self-reported numbers when both exist.
- If the user asks "would this impact me / should I be worried" — cross-reference against `customer_context.md` (industry, country, tech stack if known, watchlist) explicitly, and say so plainly: what matches, what doesn't, and what's still unknown. Don't manufacture certainty the data doesn't support.

### PIR / intel requirements briefing — currently paused

**STATUS: Paused (2026-09-17), not currently offered.** The real PIR matches live on the separate Intelligence Requirement Results object, which is missing from the MCP server's `tc_resources` entirely — confirmed as a genuine upstream gap, not a query problem (see `reference/association_traversal.md` and tracker item G). The only MCP-reachable alternative is a keyword-replication approximation with confirmed low yield, and presenting that as if it were the platform's real PIR matching would be misleading rather than useful.

**Don't proactively run PIR checks** — not as a standalone "what's new from my intel requirements" request, and not as a supplementary signal inside daily triage or industry/country scans (removed from both below). If a user explicitly asks about PIR/intel-requirement status, explain the limitation plainly (the real match data isn't reachable from here right now, pending an MCP server fix) rather than running the approximation and presenting it as reliable. Revisit this section once the MCP server team adds the missing object type — the reference material and confirmed query patterns in `association_traversal.md` are preserved for that point, not deleted.

### Daily triage — "what should I prioritize reviewing this morning"
- Requires the customer's priority signals from `customer_context.md` (recency / severity-confidence attributes / tags — whatever combination they set; **PIR matches is currently excluded as an option, see below**). If not yet captured, ask before answering, then save it.
- Pull recent items (last 24h by `dateAdded`/`publishDate`) scoped to relevant `owner`(s), rank by the customer's stated signals, present a short prioritized list (not everything that came in), with a one-line "why this made the list" per item.
- **Check for new critical CVEs directly, not just Reports/Events that happen to mention one.** A broad "what's new" sweep on `typeName IN ("Report","Event")` alone can miss a freshly-added Vulnerability object that hasn't been written up in a report yet — add a direct `typeName EQ "Vulnerability"` check (optionally scoped by CVSS threshold) alongside the Report/Event sweep.
- If IOC volume/severity is one of the customer's stated signals, use the score-based pattern in `reference/ioc_scoring_and_topic_queries.md` (`threatAssessScore`/`calScore`/`falsePositiveCount`) rather than presenting raw, unscored IOC counts.
- **PIR checks are currently paused, not a scoping option here** — see the "PIR / intel requirements briefing" section above. If the customer specifically asks for PIR matches to be included, explain the limitation rather than running the low-yield approximation.

### Industry / country / regional impact scan — "is there new intel impacting finance / my country"
- Requires industry/country — check whether the user already named it in the request itself before asking; only fall back to `customer_context.md`/asking if it's genuinely not stated anywhere.
- **Search beyond `summary CONTAINS` — also check tags and description attributes.** For country names especially, a curated report may name the country only in its full text (the `Description` attribute) or via a dedicated country/region tag, not in its own title. Combine `summary CONTAINS "<name>"` with `hasTag(name CONTAINS "<name>")` and, when it's worth the cost (see the performance caution in `reference/unified_object_queries.md`'s npm example), `hasAttribute(typeName = "Description" AND text CONTAINS "<name>")` for broader recall.
- Search recent `groups` + relevant tags/attributes for industry or geo signals (sector tags, targeted-country attributes are common in curated reports — check `tc_describe` output for the actual attribute/tag names in this instance, they vary). **Expand the user's named industry to its adjacent terms per `reference/industry_synonyms.md` before searching — don't query only the literal word the user typed.** Confirmed live: "finance" alone misses "bank"/"insurance"/etc. content that's clearly finance-relevant.
- **For short country names/codes (≤4 characters, e.g. "US," "UK," "UAE"), don't rely on bare `summary CONTAINS` alone** — a short substring match is prone to false hits inside unrelated words (confirmed live: "UK" matched inside "Ukraine"/"Ukrenergo"). Prefer the full country name and the dedicated country/region tag (`hasTag(name CONTAINS "United States")`) as the primary signal, and only add the short code as a supplementary check, calling out that it's the weaker/noisier of the two if you use it.
- **Distinguish "mentions this industry/country" from "specifically targets/affects" — this is a real, confirmed gap, not just a theoretical caution.** A text/tag search for an industry keyword (e.g. "financial") will catch victims described as having "financial records" stolen even when the victim itself isn't a finance-sector company, and will catch source/outlet names that happen to contain the keyword (e.g. "FinanceFeeds," "Sina Finance") with zero industry relevance. Skim each hit before including it, and call out any pattern of false positives you filtered out rather than silently dropping them.
- **PIR checks are currently paused, not applied here either** — see the "PIR / intel requirements briefing" section above.

### Ad-hoc / exploratory — anything else
- Fall back to the core retrieval pattern above. When genuinely unsure which group types are relevant, run `tc_resources`/equivalent once to confirm the org's actual set (custom TIP instances can add types) rather than assuming the defaults in `reference/group_types_taxonomy.md`.

### IOC lookup — "have we seen this IP/hash/domain" / a pasted list / an uploaded CSV of indicators
- Very common real-world ask, in three shapes: a single IOC, a handful pasted into chat, or a bulk CSV. See `reference/ioc_batch_lookup.md` for the full mechanics (input handling, the 15-item inline limit, batched `summary IN (...)` queries by type, which fields to request, and output shaping).
- **Always request the full context field set, every time — not just the base match.** `fields=threatassess,associatedGroups,tags,geoLocation,dnsResolution,whoIs` on every IOC lookup, single or batched, no exceptions: score/confidence, which reports/other objects reference it (context vs. isolated), and enrichment (geo/DNS/WHOIS) where available. A lookup that returns only "found/not found" without this context isn't doing the job this workflow is for.
- Core value for the user: does TC know about it at all, what's its score/confidence, how many reports/other objects reference it (context vs. isolated), and what enrichment (geo/DNS/WHOIS) is available — not just a yes/no.
- Output format follows input format: chat-pasted IOCs (≤15) → markdown table in the reply; CSV upload → enriched CSV file back.

### Case / investigation triage — "what's in my open cases that needs attention" / "who's assigned to X"
- Query `cases` directly — this is a different object family from intel (Groups/Indicators), covering the org's own investigation workflow. See `reference/object_field_reference.md` for the full field list.
- For overdue/attention-needed framing: filter on `status`, `severity`, and the direct SLA-breach booleans `detectionOverdue`/`responseOverdue`, plus `missingArtifactCount` for incomplete evidence collection. Don't just sort by date — surface *why* something needs attention (overdue, missing artifacts, unassigned).
- **Flag likely-stale results, but don't auto-filter them out by default.** Confirmed live: `responseOverdue = true OR detectionOverdue = true` returned 221 hits, and inspection showed many are old (2021–2022) with deleted user accounts on the assignee/creator fields — plausibly stale test/demo data rather than live investigations. But don't default to silently excluding these: the user might genuinely want to see everything overdue (e.g. validating that test/dev cases show up correctly, or auditing exactly what's aged in the system). Default to returning the full overdue set, and **surface staleness as a visible signal alongside each result** — recent vs. old `lastUpdated`, active vs. deleted assignee/creator — rather than deciding on the user's behalf what counts as "real." If the list is long and the user seems to want only active work, offer to narrow it (e.g. by `lastUpdated` recency) as a follow-up, the same way large result sets are handled elsewhere in this skill (see `reference/citations_and_links.md`) — an offer, not an automatic filter. Note also that `lastUpdated` recency alone isn't a reliable staleness signal either way: it can be bumped by automated/background workflow activity, not just genuine human attention (confirmed: a case named "Automated Task Test" had a very recent `lastUpdated`).
- For "who's working on X": `assigneeName`/`targetType`/`targetId`, or `createdBy`.
- To pull a case's related intel: `hasGroup()`/`hasIndicator()`/`hasArtifact()`/`hasTag()`/`hasNote()`/`hasTask()` nested queries, or expand a specific case's associations directly.

## Report generation

**Always ask the user's preferred format/template before generating anything** — don't default silently. Ask:
- Format: inline chat summary, markdown doc, or a specific house template/style they already use (check the project for an existing template before asking, if one might be present)
- Depth: quick brief vs. full write-up with sources/IOCs/associations listed
- Any standing report structure they use for this customer/engagement (save it once captured, like the customer context, so repeat requests don't re-ask)

Only after that, produce the artifact/file. Never assume a default report style for a first-time report request in a given engagement.

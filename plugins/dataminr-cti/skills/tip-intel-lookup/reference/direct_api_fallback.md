# Direct API Fallback & Custom Actions Beyond MCP

**STATUS: Deferred, not currently active.** This file is preserved as reference material for a possible future v2 release. It is not wired into any workflow in `SKILL.md` — the customer decided not to accept the security tradeoff of passing a raw API token through this chat interface, and this environment has no secure channel (like MCP's out-of-context token exchange) to supply one otherwise. Everything below remains accurate as documentation, but should not be acted on until this decision is revisited.

---

Every operation this skill uses is a thin wrapper around the same ThreatConnect/Agentic TIP **v3 REST API**. Use this file in two situations: (1) the MCP server isn't available at all, or (2) the MCP server *is* available but the user needs something outside its resource-type coverage (see the gap table below) — in that case, use MCP for everything it covers and drop to direct API only for the specific gap.

**Source of truth:** the auth and endpoint-shape details below are drawn directly from ThreatConnect's own developer documentation (`docs.threatconnect.com`), fetched and confirmed on 2026-09-17. The MCP-vs-direct-API gap comparison is confirmed live against this instance's actual `tc_resources` output, compared against ThreatConnect's own published v3 endpoint list, also on 2026-09-17. **The HTTP calls themselves are not live-tested in this environment** — there are no direct API credentials available here. Treat the shape of each call as authoritative (it's official documentation, not a guess), but verify the first real call against a live instance before relying on it further, the same discipline used everywhere else in this skill.

## Prerequisites to get from the customer

- **Instance base URL** — `https://app.threatconnect.com` for ThreatConnect's Public Cloud, or the customer's own instance URL for Dedicated Cloud/On-Premises (e.g. `https://companyabc.threatconnect.com`). The API itself lives under `<base_url>/api`.
- **API token** — generated by an Organization Administrator for an API user account (Org Settings → Membership tab → Create/Edit API User → Generate Token). Token strings start with `APIV2:`. **Use token auth only** — this skill does not use the alternate Access ID/Secret Key (HMAC) authentication method ThreatConnect also supports, since it needs a request-signing flow this skill has no reason to implement.
- Never ask the customer to paste a raw token into chat if a more secure path exists (password manager/credential tool); if they do share one directly, treat it as sensitive and don't echo it back or log it anywhere unnecessary.

## Auth — confirmed header format

```
Authorization: TC-Token <API_TOKEN>
```
This is the only header the request needs for token auth (no separate `Timestamp` header — that's only required for the Access ID/Secret method, which this skill doesn't use). Example, straight from ThreatConnect's own docs:
```
curl --location --request GET 'https://app.threatconnect.com/api/v3/indicators' \
  --header 'Authorization: TC-Token APIV2:430:c8mTcH:1234567890123:7mbiy0OnuSIq0ujNbkrqEB3RlpplzNL3CcQsYGso8ZQ=' \
  --header 'Accept: application/json'
```
**Correction to an earlier version of this skill:** the MCP server's own endpoint (`POST /api/v3/mcp`) accepts either `Bearer <token>` or `TC-Token <token>` per its README — but for the *general* v3 REST endpoints covered in this file, ThreatConnect's official documentation only specifies `TC-Token`. Use `TC-Token` for every direct-API call in this file; don't assume `Bearer` works outside the MCP endpoint specifically.

## Endpoint pattern

```
<base_url>/api/v3/<resource_type>
```
Resource types match the MCP `resource_type` values for anything MCP covers (`groups`, `indicators`, `intelRequirements`, `cases`, `tasks`, `tags`, etc.) — same names, same TQL, same field names, just plain REST instead of MCP JSON-RPC.

## Discovering fields and TQL keywords authoritatively — use OPTIONS, don't guess

This is the single biggest advantage direct API access has over MCP-only for query-building. Every v3 endpoint supports:
```
OPTIONS /api/v3/<resource_type>           → object descriptor: every field, its data type, and a description. Add ?show=readOnly to include read-only fields too.
OPTIONS /api/v3/<resource_type>/fields     → valid values for the ?fields= query parameter (nested expansions)
OPTIONS /api/v3/<resource_type>/tql        → the authoritative list of valid TQL filter keywords for this resource type
```
**This directly solves the exact class of problem this skill hit repeatedly over MCP** — `tc_describe` gives data-model fields but not reliably the TQL keyword name, which is how the `name`-vs-`summary`, `groupType`-vs-`typeName` confusions happened (documented in `tql_reference.md`). `OPTIONS /api/v3/groups/tql` would have answered those directly instead of trial-and-error. **When direct API access is available, call the relevant `OPTIONS .../tql` before constructing a TQL query for a resource type this skill hasn't already confirmed the keywords for** — it's cheap, authoritative, and removes the guessing entirely.

## Operation mapping (for anything MCP already covers)

| MCP tool | REST equivalent |
|---|---|
| `tc_resources` | `GET /api/v3/` for the endpoint index, or rely on the confirmed list below |
| `tc_describe(resource_type)` | `OPTIONS /api/v3/<resource_type>` for the object descriptor; `OPTIONS /api/v3/<resource_type>/tql` for TQL keywords specifically (see above — more reliable than `tc_describe` was over MCP) |
| `tc_list(resource_type, tql, fields, ...)` | `GET /api/v3/<resource_type>?tql=<url-encoded TQL>&fields=<comma list>&resultLimit=<n>&resultStart=<offset>&owner=<name>&sorting=<field> <ASC/DESC>` |
| `tc_get(resource_type, id)` | `GET /api/v3/<resource_type>/<id>` |
| `tc_create(resource_type, body)` | `POST /api/v3/<resource_type>` with JSON body |
| `tc_update(resource_type, id, body)` | `PUT /api/v3/<resource_type>/<id>` with JSON body |
| `tc_delete(resource_type, id)` | `DELETE /api/v3/<resource_type>/<id>` |

## What MCP already covers — confirmed by direct comparison, don't assume otherwise

Live `tc_resources` on this instance returns 28 resource types: `indicators`, `groups`, `victims`, `victimAssets`, `attributes`, `intelRequirements`, `cases`, `tasks`, `artifacts`, `notes`, `workflowEvents`, `workflowTemplates`, `owners`, `users`, `userGroups`, `ownerRoles`, `systemRoles`, `systemSettings`, `exclusionLists`, `tags`, `securityLabels`, `posts`, `notifications`, `attributeTypes`, `dataStore`, `batch`, `jobs`, `playbooks`. **This is broader than earlier versions of this skill assumed** — owners, users, jobs, playbooks, exclusion lists, and system settings are all reachable via MCP already (`tc_list`/`tc_get`, read-only per their `writable: false` flag). Don't reach for direct API on any of these just because they sound administrative — check this list first.

## What genuinely needs direct API — confirmed gaps, compared against ThreatConnect's own published v3 endpoint list

| Endpoint | Why it's a gap | What it's for |
|---|---|---|
| `POST /v3/indicators/enrich` | Action endpoint, not a listable resource — doesn't fit MCP's generic list/get/create/update/delete-by-id pattern | Trigger on-demand enrichment (e.g. DomainTools/VirusTotal lookup) for a specific indicator |
| `GET /v3/intelRequirements/results` | Confirmed elsewhere in this skill (`association_traversal.md`) — the real PIR match set with triage metadata (`score`, `isFalsePositive`, `isArchived`). **For bulk multi-PIR checks after short-listing** (see `association_traversal.md`): `?tql=hasIntelRequirement(uniqueId = "PIR-1" OR uniqueId = "PIR-2") AND lastMatchedDate > "NOW() - 24 HOURS" AND intelType IN ("Event","Report")` — checks several short-listed PIRs in one call instead of one at a time. | PIR briefings where triage status matters, or bulk-checking a short-listed set of PIRs at once |
| `GET /v3/intelRequirements/categories`, `/v3/intelRequirements/subtypes` | Taxonomy/metadata sub-endpoints, not in MCP's resource-type enum | Enumerating valid categories/subtypes when building or filtering PIRs |
| `GET /v3/job/executions`, `/v3/playbook/executions` | Execution *history* — MCP's `jobs`/`playbooks` resource types cover definitions, not run logs | Checking whether a feed/playbook actually ran, or why it failed |
| `POST /v3/token/api`, `/v3/token/svc` | Token issuance/rotation — an administrative action, not a resource | Programmatically generating or rotating an API token |
| `POST /v3/apps/exchange/install` | App-marketplace installation | Installing a TC Exchange app — unlikely to come up in intel-lookup work, included for completeness |
| Bulk `DELETE /v3/<resource_type>?tql=<...>` | MCP's `tc_delete` only deletes by single ID; the direct API supports bulk deletion filtered by TQL across an entire resource type (if enabled in the instance's system settings) | Any bulk-cleanup ask — treat as a genuinely destructive, high-caution operation; confirm explicitly with the user before ever constructing one, the same as any other irreversible action |

**Not a gap, don't over-scope:** `groupAttributes`/`indicatorAttributes`/`caseAttributes`/`victimAttributes` appear as separate endpoints in ThreatConnect's docs, but MCP's single generic `attributes` resource type almost certainly covers all of them with type-scoping — this hasn't been explicitly tested, but treat it as one gap to verify rather than four.

## Pagination

Same shape as MCP: responses include `count` (first page only) and either a `next` URL or pagination params (`resultStart`/`resultLimit`) to continue. Follow the same triage-then-expand approach from `association_traversal.md` — don't fetch every page by default.

## Error handling

Malformed TQL or bad params return HTTP 400 with a JSON body naming the exact rejected field (same error shape observed via MCP, since MCP is just forwarding it) — read the message, don't retry the same guess.

## Practical notes for this environment

- `web_fetch` can only retrieve URLs that have already appeared in the conversation (the customer's own instance URL, once given, counts) — it can't blindly construct arbitrary new hostnames from memory. Confirm the exact base URL with the customer first.
- Never place the API token in a URL query string — always as the `Authorization` header. If the available fetch tool can't set custom headers, flag this limitation to the user rather than working around it insecurely.

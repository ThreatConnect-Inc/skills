# ThreatConnect Playbook app types — what they mean and what to read

Each job in `jobList` has `appCatalogItem.programName` (or `.displayName`) naming its app, and a `jobParameterList` array of `{appCatalogItemParameter: {paramName}, value}` pairs. What to look at differs a lot by app type — use this to know which params actually matter before reading a job in full.

## Base Agent — an LLM call
The core generative unit. Look at:
- `systemPrompt` — the instructions/schema/rules (often long, several KB — this is where the real behavior lives)
- `userPrompt` — what gets filled in per-call, usually references to other jobs' outputs via `#App:<id>:<field>!<Type>` syntax
A system prompt with a big "OUTPUT SCHEMA" block and a "SELF-CHECK" checklist at the end is this project's house style — expect strict JSON-only output, no markdown fences, explicit self-verification steps.
- **"OUTPUT SCOPE" sharding**: it's common to see several near-identical Base Agent jobs (e.g. three "Content Synthesizer" jobs, three "Section Builder" jobs) that share almost the entire same system prompt verbatim, differing only in a short "OUTPUT SCOPE" clause restricting which top-level schema keys that particular job is allowed to emit. This is a fan-out-by-output-domain pattern, not a fan-out-by-input-data-slice — all of them typically receive the *same* full input; don't assume one is working on a smaller slice of the data just because there are several of them.
- Don't rely on an LLM job to do a deterministic lookup/join between two lists (matching a code against a lookup table, say) — confirmed unreliable even with an explicit, clear instruction. See the "LLM-based matching/joins" note in `references/gotchas.md`.
- **A Base Agent can be given a live "Knowledge" context** — a `userContext` entry of `knowledgeType: "DataModel"`, `searchType: "TQL"`, with its own `dataModelType` (e.g. `Groups`), a TQL `key`, a `variableName`, and `results` shape options (`includeTags`, `limit`, `maxAssociations`, etc.) — configured in Designer, not something a raw JSON build can easily hand-roll from scratch (copy an existing one and edit the TQL/variableName instead). This runs a live query against the instance and makes the result available to the prompt via `#Knowledge:<jobId>:klg.datamodel.<variableName lowercased>!String`. Confirmed use: giving an entity-extraction agent the instance's own existing inventory (e.g. "these are the intrusion sets/malware already tracked") so it can recognize an alias of something that already exists instead of creating a duplicate under a new name — see EXT-5 in `best_practices.md` for the prompt-design pattern this enables (and the pitfall it also enables if worded carelessly).
- **A job's own `outputVariables` declaration doesn't have to resolve for the pipeline to activate/run.** Confirmed: a Base Agent's `outputVariables` can read back as `[]` after every push (even when explicitly set) and the playbook still activates and runs correctly, because what actually matters is the connection edge between producer and consumer (see the `#App:` note below) — don't treat an empty `outputVariables` as proof a job's output isn't wired up or working.

## TCPB - ThreatConnect API v3 — a live TQL fetch
Look at the `params` array (itself a JSON string, parse it): usually has `tql`, `resultLimit`, and one or more `fields` entries (field expansion, e.g. `tags`, `attributes`, `associatedGroups`, `associatedIndicators`, `common`, `linkedGroups`). Also `url` (e.g. `/v3/groups`, or `/v3/groups/{id}` for a single-entity GET) and `http_method`.
- `fields=common` attaches the platform's normalized `commonGroup` object (CVSS for Vulnerabilities, `priority`/`mitreId` for Threat Actor Profiles) — worth specifically checking whether a given fetch requests it, since it's easy to miss and changes what data is actually available downstream.
- The `tql` value is usually built from several `#App:...`/`#Global:...` variable references concatenated together — reconstruct the full expression by resolving each reference to see the actual query that runs.

## TCPB - JMESPath v3.0 (or v2.0) — a deterministic transform
Look at `json_data` (the input expression/reference) and `string_expressions`/`string_array_expressions` (the actual JMESPath, as `{"key": "output_name", "value": "<expression>"}` pairs). This is where data gets reshaped/filtered/scored without any LLM involved — the "Shape"/"Extract"/"Merge" naming convention in this project's playbooks usually marks these.
- **`#App:`/`#Global:` references substitute directly into the expression text itself, not just into `json_data`** — confirmed working pattern: an expression like `union(#App:<id>:field!StringArray, #App:<id2>:field2!StringArray)` has both references replaced with their literal JSON-array text before the expression is parsed, so you can combine two *different* jobs' outputs in one expression without funnelling them both through `json_data` first.
- **JMESPATH-UNION: `union(array1, array2)` is a confirmed-working TC-custom function that combines two arrays AND dedupes them** (confirmed on instance C, 2026-10-21, via a disposable sandbox test — not in the standard JMESPath spec and not stubbed by the local Python `jmespath` package, so it can't be checked with `jmespath_local_test.py`; verify any new use of it live). This is the correct tool for combining two always-present arrays — see the `Merge` entry above for why `Merge` itself is the wrong tool for that job.
- **A declared JMESPath output's `.count` suffix does NOT work the way `.count` does on some native app outputs (e.g. Doc Analysis's own `tc.parsed.<x>_array.count`).** Confirmed: referencing `#App:<jmespathJobId>:<myvar>.count!String` on a JMESPath job's own declared StringArray output failed activation with `Invalid Variable Reference`, even though the identical-looking `.count` pattern works fine on Doc Analysis's native outputs. `.count` is app-specific, not a generic platform feature on any StringArray-typed variable. If you need a count of a JMESPath job's own output, compute it explicitly as its own declared output: `to_string(length(x || \`[]\`))`.

## TCPB - Regex Operations v2 ("Python Regex Operations") — regex replace/extract on a string
Confirmed working shape for `tc_action: "Replace"`: `input_replace` (the source string reference), `regex`, `replace` (the replacement text), `flatteninput`, `stripnull`. Output is always a String under the fixed variable name `regex.match.0` regardless of `tc_action` — this app does not rename its output per-action.
- **The correct `tc_action` value for an extract-a-substring mode is not confirmed.** Two guesses (`"Extract"`, `"Match"`) were both tried against a live instance and both silently produced no output (HTTP 200, empty body) with no diagnostic to learn from — consistent with this project's general "guessing at an unfamiliar app's exact enum/param values burns rounds with no feedback" pattern (see the Designer-template-job technique in `dataminr-playbook-builder`'s SKILL.md). If you need this app's extract mode, don't keep guessing: ask the user to configure one such job directly in Designer and fetch it back as a working template, the same technique already recommended there for this class of problem.
- If you only need "pull the JSON object out of a string that may have prose before/after it" (e.g. to make a downstream strict-JSON parser tolerant of a chatty LLM response), a working alternative that doesn't depend on resolving this gap: fix the root cause in the LLM's own prompt (see JSON-8 in `best_practices.md`) rather than trying to paper over it with a regex-extraction step.

## Template Builder — Freemarker (FTL) rendering
Look at `template` (the FTL source — `<#assign>`, `<#function>`, `<#list>` etc.) and `inputs` (what variables get bound into the template). This is the final, non-agentic assembly step that turns structured JSON into HTML — no LLM call happens here, so it's the one place in the pipeline with fully deterministic/repeatable output. If one of these jobs is erroring, read `references/ftl_debugging.md` before guessing at FreeMarker semantics — it covers several confirmed, non-obvious failure modes (`?then` isn't short-circuiting, null arguments fail at the call site not inside the function, empty-string `?eval_json`, etc.).
- When a template builds a link to a TIP object, check for an existing base-URL-deriving variable already in scope (often named something like `origin`) before adding a new one — different TIP object types use different URL shapes (modern `/#/details/<type>/<id>` SPA routes vs. legacy `/auth/<type>/<type>.xhtml?<type>=<id>` pages for some object types like Tags), so don't assume one pattern covers every link a template needs.

## If / Else — a native branch
Look at `operand_1`, `operand_2`, `operator` (e.g. `equals`), `as_numeric`. Only one branch's downstream jobs actually execute at runtime — if you see two near-identical jobs (e.g. one named "Copy of X"), check which branch each sits on via `playbookConnectionList` before assuming they're redundant; they're very likely each serving one branch of an `If/Else`.

## Iterator — a native loop over array(s)
Feed it one or more equal-length arrays (or a single array, or a dummy array); it runs a set of steps once per index. Each iteration is independent by default — no automatic carry-over of data from one iteration to the next. Iterations run **sequentially** (confirmed), and a fetch/API-call step can live inside an iteration, parameterized by the current index (confirmed) — this is the mechanism for paginating through a large result set without a fixed resultLimit.

## Cache Store — cross-iteration / persistent state
Used alongside Iterator to carry a running value across iterations (e.g. "current page number," or a running top-K candidate list) via read-then-write — safe here specifically because iterations are sequential, not parallel (a parallel iterator would risk a race on this read-modify-write pattern).

- **Closing the loop does NOT require a `Merge` app.** The `EndLoop`-type connection back to the Iterator's own job id can originate from any ordinary job — confirmed with the last job in the loop body (e.g. a `ThreatConnect Update Groups` call) wired directly `--EndLoop(circular)-->` the Iterator, no `Merge` job in between. An earlier design used `Merge` purely as a loop-closing placeholder; that's unnecessary ceremony — reserve `Merge` for jobs that actually need to combine/coalesce two different values (see below).
- **Getting something to run "after the loop finishes" is a form of fan-in and may not work.** Iteration-by-iteration execution of the loop body is confirmed reliable, but a job meant to run once after all iterations complete (as a true convergence point, not just the `EndLoop` edge back to the Iterator) hit the same branch-convergence limitation noted below. The confirmed workaround: make the loop a dead-end branch — fan it out in parallel from the same source job that starts the "real" response path, rather than gating the response on the loop completing.

## Update Global Variable — sets a `#Global:0:<name>!<Type>` variable
Look at `variable` (the global being set), `operation` (usually `Set`), and `value` (what it's set to, usually another job's output). Globals set this way are readable from any later job via the same `#Global:0:<name>!<Type>` syntax, regardless of which branch set them.

## Merge — combines multiple jobs' outputs
Look at `output_array`: a `{"key": ..., "value": ...}` where `value` is often a straight concatenation of two (or more) job output references with no separator. When the inputs come from mutually-exclusive `If/Else` branches, this behaves as a coalesce (only one side ever has real content at runtime) rather than a true string merge — check whether the inputs are branch-exclusive before assuming it's literal concatenation.
- **`Merge` is for coalescing optional paths, not for combining two arrays that are BOTH always present** (confirmed correction from a user with direct platform experience, instance C, 2026-10-21). Using it to concatenate two StringArray outputs that are each unconditionally generated (e.g. two parallel extraction agents' results, neither ever null) silently produced a malformed, unusable value — and a more subtle confirmed failure mode: the `Merge` job itself can simply vanish between push and activation when its inputs aren't actually branch-exclusive, leaving the *consuming* job with a dangling reference to a job id that no longer exists (activation still succeeds; the pipeline just silently loses that data path). If you need to combine two always-present arrays, use a `JMESPath` job with the platform's `union(array1, array2)` custom function instead (confirmed working, and it dedupes) — see JMESPATH-UNION below. Reserve `Merge` for genuine fan-in-from-mutually-exclusive-branches coalescing.
- **Don't assume `Merge` (or any shared downstream job) reliably fires when two branches converge on it.** Confirmed broken on at least one real instance (instance C), in three different shapes: a plain downstream job with two incoming Pass edges from mutually-exclusive branches, a dedicated `Merge` app used the same way, and a full production design using the same pattern — none of them fired, even though each branch worked perfectly in isolation. A similarly-shaped pattern is documented working on a different instance (instance A) elsewhere in this project, so this is platform/instance-dependent, not a universal rule. Treat branch convergence (fan-in) as something to smoke-test in isolation on a new instance before designing around it — fan-OUT (one job's Pass driving several independent downstream branches) is unaffected and confirmed reliable everywhere tested.

## TCPB - DataStore v4 — durable key/value state, native to the platform
The correct way for a playbook to persist its own state across runs (e.g. a watermark/cursor, a dedup set, a counter) — no more "create a placeholder Group and stash a value in an attribute" workaround needed. Look at `tc_action` (`GET`/`POST`/`DELETE`), `domain` (usually `Organization`), `data_type` (the bucket name, e.g. a namespace like `FEED_TIMESTAMP`), `rid_required` (the record id string, e.g. `"last_run"`), `data_required` (value to write, for `POST`), `fail_on_not_found`.
- **Never reference `datastore.data.string` directly.** It is left completely UNDEFINED (not merely empty) when the record doesn't exist, and referencing it anywhere downstream hard-crashes the whole run with no useful error. Always read the always-populated `datastore.response.json` instead (`{"found":false}` when absent, `{"found":true,"_source":{"type":"String","data":"..."}}` when present) and extract the value via a JMESPath job: `_source.data || ''`.
- **`fail_on_not_found: true` plus a Pass/Fail branch for "first run vs. subsequent run" is tempting but hits the branch-convergence limitation above** if the two branches need to reconverge afterward. The simpler, confirmed-working design: leave `fail_on_not_found: false` and let the `_source.data || ''` fallback above double as the "no watermark yet" case (an empty string compares as "before everything" in a TQL/date `>` comparison) — no branching needed at all.

## TCPB - HTTP Client v3.0 / TCPB - ThreatConnect API v3 — generic HTTP calls
Look at `http_method`, `url`, `headers`, `params` (query string, as a JSON array of `{key,value}`), and `body`. `TCPB - ThreatConnect API v3`'s `url` field supports embedded dynamic variables mid-path (e.g. `/v3/groups/#App:X:Y!String/download`) — confirmed working, useful for per-entity GETs inside a loop.
- **A `body`-type parameter silently corrupts any non-JSON payload referenced into it from another job's output.** Confirmed via byte-level diff on real multi-MB content: referencing a String-typed job output into ANY job's `body` param (on this app or similar HTTP-style apps) applies JSON-string escaping to the actual bytes sent over the wire — wraps the value in quotes, escapes embedded `"` as `\"`. The SAME value referenced directly into a trigger's `httpResponseBody` is clean/unescaped, so the corruption is specifically about referencing *into a `body` field*, not about the source app. There is no reliable fix via re-escaping at scale (a JSON re-parse breaks on real non-JSON-safe bytes; an unescape step just re-corrupts on its own output's next reference hop). If a chain needs to carry file/binary content between jobs (e.g. relaying a fetched document's bytes onward), avoid routing it through any `body` field — see `TCPB - Binary Operations v2` below for the actual working pattern.

## TCPB - Binary Operations v2 — String <-> Binary conversion
`tc_action: "Convert from String"` with `input_string` turns a String output into a Binary-typed output (e.g. `binary.outputs.0`) — the only way to get bytes into a param that requires the `Binary` type, like `file_content` on `ThreatConnect Update Groups` below. This is also the way to move file/binary content between jobs without hitting the `body`-field corruption bug above, since none of its own params are `body`-type fields.
- **Known defect:** non-ASCII punctuation (smart quotes `“`/`”`, em-dashes) gets replaced with a literal `?` (0x3F) during the conversion. No visible encoding parameter avoids this — treat as an accepted limitation unless a cleaner fix is found later.

## TCPB - Threatconnect Get Groups v2 / TCPB - Threatconnect Update Groups v1 — the file-attachment pattern
`Update Groups`' `entities` param needs a typed `TCEntity` object, not a bare numeric id. Resolve one with `Get Groups` using `tc_action: "ID"` and `group_id: <numeric id>` (NOT `tc_action: "Entity"`, which expects a trigger-supplied entity and doesn't work for a bare-id lookup inside a webhook/loop context) — its output `tc.group.entity` (type `TCEntity`) feeds directly into `Update Groups`' `entities` param. Combine with `entities` + `file_content` (a `Binary`-typed reference, from `Binary Operations` above) + `file_name` + `group_type` to attach a file to an existing group. Confirmed working at real multi-MB file sizes, byte-identical aside from the Binary Operations Unicode defect above.
- These are both newer "business" apps whose `outputVariables` can get silently stripped back to `[]` by the server on a raw API push unless the REST of the job (especially `tc_action` plus its companion params) matches exactly what the Designer UI would produce for that action — if a custom output name isn't sticking, don't keep guessing param combinations; copy a Designer-saved example of that exact `tc_action` instead (see `gotchas.md`).

## TCPB - ThreatConnect Batch Import v2 — bulk group/indicator/association upsert
`import_data` takes a JSON string shaped `{"group":[...],"indicator":[...],"association":[...]}`. Supports xid-based upsert (submitting the same `xid` again updates that entity in place rather than creating a duplicate) across group and indicator types in one call, plus a top-level `association` array (`{"ref_1": xid, "ref_2": xid_or_summary, ...}`) for arbitrary cross-type associations without a separate API call per link.
- **A fully-empty payload hard-crashes the run.** `{"group":[],"indicator":[],"association":[]}`, or even a literal `{}`, causes a silent, unrecoverable failure (empty webhook body, no error surfaced) — confirmed, not yet solved generically. If the upstream data can legitimately be empty on some runs (e.g. a time-gated sync that sometimes has nothing new), guard for it explicitly before this job rather than assuming an empty-but-valid payload is safe.

## Logger — a debug tap
Usually just passes content through for visibility in the execution log; rarely carries meaningful configuration beyond what it's logging.

## Agent trigger — an Ask AI chat agent (confirmed instance A/B, Oct 2026)
Trigger `type: Agent`, `eventType: External`, `chatTriggerTypes: Global` (report agents use `Reporting_GroupDetail,Reporting_Configuration` instead). Key fields: `outputVariables` declares `trg.agent.body` (the user's message, String; `trg.agent.chatconversationid` also exists) and report agents `trg.agent.entity`/`trg.agent.addl_ctx_json`; `httpResponseBody` = the reply shown in chat (reference the final Merge or agent output); `conversationHintJson` = the example prompts; `overrideRunAsUser: true` runs as the chatting user; `contextWindowSize` = turns kept; `pipeOutputParams` is an optional mapping seen in existing agents. The Base Agent's `messageContextWindow` controls how much earlier chat it sees (set >0 on an extractor so a follow-up like "now give me the Splunk queries" can recover the subject; 0 on workers fed everything in the prompt). The playbook `description` is what the router uses: write "Use when ... Not for ...". Omit `scheduleType` when creating. After activation the Ask AI "Available agents" panel lists the agent with its description. The agent URL `/api/agent/<uuid>` returned an empty 200 to a plain POST (not a test path).

## Native object-event triggers (e.g. `type: Report`/`Group`, `eventType: AddTag`) — batch-reprocessing reliability
Fires on a native TC object lifecycle event (a tag transitioning from absent to present, a field changing, etc.) rather than a webhook/chat call — see `dataminr-playbook-builder`'s SKILL.md for how to test one of these at all (there's no endpoint to call; you mutate a real object and read the result back). Confirmed gotcha when using this to **reprocess many objects at once** (e.g. re-tagging dozens of existing items to force a batch run through an already-built pipeline): the trigger does not reliably, promptly fire for every item in a tight batch of near-simultaneous mutations.
- Two tag-cycling attempts against ~32 objects (delete-then-re-add the trigering tag) — one with all deletes followed by all re-adds in two tight loops, one with a 2-second stagger between each object's delete+re-add — both left the large majority of objects showing no sign of having reprocessed when checked shortly afterward (minutes to tens of minutes) via the API.
- This turned out NOT to mean those events were silently dropped: checking back much later (and separately, confirming via the Designer UI rather than an API-based freshness heuristic) showed the full batch had in fact completed. **Don't conclude a batch has stalled from an indirect freshness signal alone** (e.g. an attribute's `dateAdded` timestamp not having a new entry) — cross-check the actual target data you care about (the real associations/fields the pipeline writes) or the Designer UI before concluding anything is stuck. The true behavior looked like a long, uneven processing queue under batch load, not reliably predictable from per-item latency.
- Practical implication: budget significantly more wall-clock time for a bulk reprocessing job through this trigger type than "number of items x typical single-item latency" would suggest, and don't design a test or rollout around a tight time window for this kind of batch.

## Cache Store / Cache Lookup — per-conversation state for chat agents (confirmed, Oct 2026)
`Cache Store`: `cache_name` (e.g. `Prefix-#Trigger:<id>:trg.agent.chatconversationid!String`), `cache_key`, `content`, `expire_seconds`; no outputs. `Cache Lookup`: same `cache_name`/`cache_key`, `fail_on_miss`, output `cache.lookup.results` (String); with `fail_on_miss: true` use a Fail edge to a message job. Use a dead-end branch for the store so the reply is not gated on it.

## TCPB - JSON Operations v1 — `Build JSON` (and a creating-a-case note)
Params `tc_action` `Build JSON`, `json_data_build`, `indent` (4 works; 0 was not confirmed), `sort_keys`; output `json.formatted`. See the gotchas for the whole-string-reference rule. Creating a Case uses the generic `TCPB - ThreatConnect API v3` (`POST /v3/cases`); there is no dedicated Cases app in the instances checked.

## Variable reference syntax (appears everywhere, in every app's params)
- `#App:<jobId>:<fieldName>!<Type>` — another job's named output
- `#Global:0:<name>!<Type>` — a global variable
- `#Trigger:<triggerId>:<fieldName>!<Type>` — a value from the trigger itself
`<Type>` is usually `String`, sometimes `TCEntity` or others. To trace a value's origin, find the job with that id in `jobList` and look at its own outputs/params.
- **An `#App:<jobId>:...` reference also requires a matching connection edge in `playbookConnectionList` from that producer job to the consuming job — the variable string alone is not enough** (confirmed on instance C, 2026-10-20: a new job wired with the reference string but no corresponding edge failed playbook activation with `Invalid Variable Reference in Parameter(s)`, naming the consuming job). When reviewing or building a playbook, don't just trust that a `#App:` reference resolves because the syntax is well-formed — check that `playbookConnectionList` actually has `{sourceJobId: <producer>, targetJobId: <consumer>}` (or a chain of edges connecting them transitively).
